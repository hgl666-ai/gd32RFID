# 调试版本使用说明

> 本版本用于排查"甲方发送命令无回复"的问题。
> 串口会输出协议命令的收发过程和CRC校验结果，帮助定位通信故障。

---

## 一、串口配置

| 参数 | 值 |
|------|-----|
| 波特率 | 115200 |
| 数据位 | 8 |
| 停止位 | 1 |
| 校验位 | 无 |
| 显示模式 | **文本模式（ASCII）** |

**重要**：调试版本请用**文本模式**查看串口输出，不要用HEX模式。调试信息是可读文本，MCU发送的二进制应答帧会显示为乱码，可以忽略，因为 `[TX]` 行已打印应答帧的完整HEX内容。

---

## 二、调试输出格式

上电后串口会输出（仅几行，不刷屏）：

```
[SYS] GD32E230 RFID Jul 18 2026 10:00:00
[SE] Auth OK              （或 [SE] Offline, passthrough mode）
[SYS] Ready. Waiting for commands...
```

看到 `[SYS] Ready` 后，即可发送命令。每发送一条命令，串口会输出收发过程：

### 收到正确命令时：
```
[RX] OK CMD:01 LEN:00 CRC:6B03
[CMD] QueryUID -> replying
[TX] UID Resp: A5 5A 01 0C 39 53 48 85 13 46 54 50 41 38 54 56 56 C1
```

### CRC校验失败时（甲方最可能出错的地方）：
```
[RX] CRC ERR! CMD:01 LEN:00 RECV_CRC:1234 CALC_CRC:6B03
    Correct frame should be: A5 5A 01 00 6B 03
```
- `RECV_CRC` 是甲方实际发送的CRC
- `CALC_CRC` 是MCU计算的正确CRC
- 最后一行给出了**正确的完整帧**，直接复制即可

### 命令码或长度不匹配时：
```
[CMD] CMD=01 but LEN=40 (expected 0 for UID query)
[CMD] CMD=02 but LEN=10 (expected 16 for KEY write)
[CMD] Unknown CMD=0x03 (only 01/02 supported)
```

### 长度异常（LEN>250）时：
```
[RX] LEN ERR (LENGTH > 250, frame rejected)
```

## 三、如何根据输出定位问题

| 现象 | 原因 | 解决方法 |
|------|------|---------|
| 发命令后**没有任何输出** | 串口没连通 | 检查TX/RX是否接反、是否共地、波特率是否115200 |
| 只有 `[SYS] Ready`，发命令后无 `[RX]` | 命令没到达MCU | 检查串口工具是否**HEX发送**模式、帧头是否 `A5 5A` |
| 出现 `[RX] CRC ERR` | CRC计算错误 | 对比 `RECV_CRC` 和 `CALC_CRC`，或直接用给出的正确帧 |
| 出现 `[RX] OK` 但无 `[TX]` | CMD或LEN不匹配 | 看 `[CMD]` 行提示的 expected 值 |
| 出现 `[RX] OK` + `[TX]` | MCU已回复 | 甲方串口工具的接收配置有问题 |

---

## 四、测试命令

### 查询UID（直接复制到HEX发送框）：
```
A5 5A 01 00 6B 03
```

### 写入KEY（示例，KEY=01 02 03...10）：
```
A5 5A 02 10 01 02 03 04 05 06 07 08 09 0A 0B 0C 0D 0E 0F 10 94 00
```

---

## 五、切换为正式版本

调试完成后，将 `Head/debug_config.h` 中的：
```c
#define DEBUG_ENABLE    1
```
改为：
```c
#define DEBUG_ENABLE    0
```
重新编译即可。正式版本串口不输出任何调试信息，只传输纯净的二进制协议帧。

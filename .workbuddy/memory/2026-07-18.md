# 2026-07-18 工作日志

## 调试版本制作（甲方发命令无回复排查）

### 背景
- 用户本地测试两条命令都能正常回复
- 甲方发送命令无回复，要求提供调试版本
- 用户将DEBUG_ENABLE=1后发现串口刷屏（信息太多太快）

### 修改内容
1. **app_protocol.c 调试输出重构**：
   - app_uart_rx_task: 收到正确帧打印 `[RX] OK CMD:XX LEN:XX DATA:XX.. CRC:XXXX`
   - CRC错误时打印对比: `RECV_CRC:XXXX CALC_CRC:XXXX` + 给出正确完整帧
   - app_process_frame: 打印命令分发 + LEN不匹配提示(expected值)
   - app_handle_query_uid/write_key: 打印完整应答帧HEX `[TX]`
   - app_rfid_poll_task: 完全静默(去掉所有DBG_PRINTF)，不刷屏
2. **main.c 精简启动信息**：去掉大段Banner/UID/KEY/FM17622打印，只保留一行 `[SYS] GD32E230 RFID`
3. **bsp_crypto.c 精简**：crypto_chip_init只在失败时打印原因(ATR failed/Auth failed)，成功时由app_protocol_init统一打印 `[SE] Auth OK`
4. **debug_config.h**：DEBUG_ENABLE=1(调试版本)，更新注释说明输出格式
5. **CRC对比功能**：CRC错误时重新计算正确CRC并打印对比，还给出正确的完整帧让甲方直接复制

### 调试输出设计
- 只有协议命令收发时才有输出（RFID轮询完全静默）
- 启动仅3行：[SYS] [SE] [SYS] Ready
- 每条命令产生3-4行：[RX] [CMD] [KEY] [TX]
- 甲方通过文本模式查看，根据输出定位：无输出=串口没连/CRC ERR=CRC算错/有[TX]=MCU已回复

### 看门狗反复复位修复（同日，关键bug）
- **现象**：甲方拿到调试版本后串口刷屏，一秒十几次重复打印启动信息
- **根因**：看门狗(200ms超时)在bsp_i2c_init后启动，但FM17622_Init+FM17622_CheckComm+crypto_chip_init初始化总耗时超过200ms，看门狗复位MCU→重启→又超时→又复位，循环
- **修复**：在main.c每个初始化步骤后插入bsp_watchdog_feed()；在app_protocol_init的crypto_chip_init前后也喂狗
- **同时**：注释掉main.c的[SYS]启动行（用户要求），只保留app_protocol_init里的[SE]+[SYS] Ready（修复后只打印一次不再刷屏）
- **教训**：看门狗启动后，所有耗时初始化步骤之间必须喂狗。200ms看门狗+软件I2C超时(每次i2c_wait_ack约3.4ms)+多个I2C设备初始化=容易超时

### 看门狗超时二次修复（同日，增大超时时间）
- **现象**：加喂狗后仍刷屏(间隔416ms重启)，说明200ms对软件I2C+多设备仍然太短
- **根因**：app_rfid_poll_task内部的FM17622 I2C操作(若通信失败每次i2c_wait_ack超时3.4ms，多次累计)也可能超过200ms
- **修复**：看门狗超时从200ms(125,DIV64)增大到1秒(625,DIV64)；app_rfid_poll_task内部RequestA后和ReadTagData后各喂狗一次
- **结论**：软件I2C+多设备(FM17622+FMSE)的项目，看门狗200ms太短，1秒是合理值

### fm_transceive看门狗超时修复（同日，"偶尔得不到回复"根因）
- **现象**：发送命令偶尔得不到回复，连续发3次只回复1次
- **根因**：bsp_fm17622.c的fm_transceive等函数有5处 `while(timeout=2000)` 轮询循环等待FM17622完成。FM17622通信失败时每次ReadReg约15ms(3次i2c_wait_ack超时)，2000×15ms=30秒，远超1秒看门狗→MCU复位→命令数据丢失
- **修复**：在FM17622_WriteReg和FM17622_ReadReg函数开头各加bsp_watchdog_feed()，这样所有FM17622 I2C操作都喂狗，2000次循环每次ReadReg都喂狗不会超时
- **教训**：任何 `while(timeout--)` 轮询循环等待硬件响应时，循环体内必须喂狗。硬件通信失败时超时累计可能远超看门狗超时

### fm_transceive阻塞修复 + FM17622离线跳过（同日，"扎堆回复"根因）
- **现象**：发7次命令前6次无回复，第7次后扎堆收到7个回复
- **根因**：fm_transceive的timeout=2000，FM17622通信失败时2000次循环阻塞约3秒，期间UART数据积压
- **修复**：①bsp_fm17622.c所有timeout=2000改为200(5处replace_all)；②新增g_fm17622_online全局变量，main.c中FM17622_CheckComm返回值存入，app_rfid_poll_task开头检查离线则直接return不执行I2C操作
